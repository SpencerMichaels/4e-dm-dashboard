# 4e DM Dashboard — Agent Context

This is the canonical repository guidance for coding agents. Keep it current as the project evolves.

## What This Is

Electron app for a DM running physical tabletop RPGs. Two windows (DM + Player), D&D 4e only, campaign data stored as JSON on disk. Built with React + TypeScript + Zustand + CSS Modules, using electron-vite as the build tool.

## User Profile

- Heavy Vim/keyboard user — wants hotkeys for everything
- Runs PF2e, D&D 4e, and Delta Green
- Strong low-level programmer, new to web/frontend — explain web-specific decisions but don't over-explain general programming
- Wants maximum automation for deterministic game mechanics (auto-decrement conditions, prompt saves, track durations)
- Strongly values human-readable, non-proprietary data (JSON files on disk, not databases)
- Prefers minimal well-known libraries; implement small utilities in-house
- Security-conscious: install packages, build, and run tests only inside the project-local Nix shell (`nix develop`, pinned by `flake.nix`/`flake.lock`), never with globally installed tools. `npm` scripts that install dependencies run there too
- The Electron GUI runs directly on the host (NixOS, Wayland). npm's Electron binary cannot run on NixOS, so the Nix shell points `ELECTRON_OVERRIDE_DIST_PATH` (the `electron` launcher) and `ELECTRON_EXEC_PATH` (electron-vite) at nixpkgs' Electron; the `electron` devDependency in `package.json` must stay on the same major as `electron` in `flake.nix`. Launch with `./launch.sh` (dev mode with hot reload; log in `$TMPDIR/4e-dm-dashboard-dev.log`)
- App data (campaigns, drafts, settings) is in `~/.config/4e-dm-dashboard`, the same directory the installed app (`./install.sh`, `default.nix`) uses. It is the DM's real data: tests and scripts must use a temporary `userData`, as the UI smoke tests do

## Working Agreements

- Preserve the human-readable, file-based data model and the main-process-as-source-of-truth architecture.
- Prefer focused changes and small, well-known dependencies. Ask before adding a production dependency.
- Do not discard or overwrite unrelated working-tree changes.
- Run package installation, builds, and tests inside the Nix dev shell (`nix develop -c <cmd>`, or `use flake` through direnv: copy `.envrc.example` to `.envrc`). Never use `nix develop path:.`: it copies the whole working tree, `node_modules` included, into the store on every call. The flake goes through git, so a new file it needs (e.g. `flake.nix` itself) must be `git add`ed first. `nix build` builds the packaged app (`default.nix`; update `npmDepsHash` when `package-lock.json` changes).
- UI tests and screenshot scripts must not show windows on the DM's desktop: set `FOUR_E_HIDDEN_WINDOWS=1` (windows are created hidden, unthrottled, and rendered offscreen; screenshots come from the `paint` event; `npm run test:authoring:ui` and `test:compendium:ui` do this) and stub `window.confirm`, which would otherwise open a native dialog and block the run.
- Run the UI suites with `npm run test:ui` (all four, or `npm run test:ui -- combat compendium`): it builds into a private `.ui-test-builds/<run>/build`, runs the suites with that run folder as their working directory (screenshots in `<run>/out/`, printed at the end), and deletes the build; it checks each suite's syntax before building (a suite that does not parse would leave Electron waiting on an error dialog) and stops a suite after 10 minutes (`FOUR_E_SUITE_TIMEOUT_MS`), so it is safe while other agents build or test in the same checkout. The `test:*:ui` scripts test the shared `out/` from `npm run build` instead, which a concurrent build can replace mid-run. The suites read published content from `FOUR_E_CONTENT_DIR`, a temporary install of the invented content repo in `tools/ui-smoke/fixtures/content-repo` (2026-11-14; written by `fixtures/make-content-repo.cjs`, never book text; `tools/ui-smoke/test-content.cjs`, built once per run by `run.cjs`), so they run without the private content repo; they load the build from `FOUR_E_OUT_DIR`. A suite that needs another published entry adds an invented one to `make-content-repo.cjs` and reruns it (a unit test keeps that repo valid). A new suite should do the same, never write into the checkout, and be added to `tools/ui-smoke/run.cjs`.
- Buttons must read as buttons before hover: a text button needs a border or a fill. A `<button>` with no class gets a bordered default (`global.css`); icon-only buttons carry an `aria-label`; never use `.ghost` for an action. List, menu, and nav rows are exempt by role. `npm run test:buttons:ui` (`tools/ui-smoke/button-audit.cjs`) tours the app and fails on violations.
- Match the surroundings: a new button or other element placed among existing elements of the same kind (sidebar rows, toolbar buttons, list rows) uses their class and styling, not a look of its own. An element with materially different semantics (an action among page links) must be recognizably different without more visual prominence than its neighbors: set it apart by position or a subtle, coordinated variant of their style, not a heavier border or fill (e.g. Close Campaign is a plain sidebar row placed at the foot of the sidebar, away from the page links).
- When changing behavior, update the relevant project documentation and add or update tests when practical.
- Keep the implementation-status section below current when completing a documented task.
- Shared 4e code (vocabulary, content schema, character snapshot, later the style kit) lives in the `4e-kit` repo, included as the git submodule `vendor/4e-kit` and imported as `@kit`. Clone with `--recurse-submodules`. Change shared code in the kit repo first, commit there, then bump the submodule here; 4ecb consumes the same repo.

## Architecture

- **Main process**: single source of truth. Owns campaign data, combat state machine, 4e rules and compendium.
- **DM renderer**: sends commands via `ipcRenderer.invoke()`, receives state via broadcasts.
- **Player renderer**: receive-only — gets stripped state (no exact HP, no stat blocks).
- **Zustand stores** in each renderer populated entirely from main process broadcasts.
- **State flow**: `DM Renderer → invoke(command) → Main Process → mutate → broadcast to both renderers`
- **4e rules module**: `src/common/rules/` (conditions, HP descriptors, creature-builder benchmarks, settings, class marks, known values) is shared by main and renderer. The compendium lives in `src/main/compendium/`, and 4e UI components live in ordinary feature folders under `src/renderer/components/` (`combat/`, `creature/`, `compendium/`, `campaign/`). There is no plugin registry, user plugin loading, or turn-hook API. The combat engine builds saves, recharges, ongoing damage, and regeneration items itself. The app was multi-system (PF2e, Delta Green) before 2026-11.
- **Combat runs on kit content** (2026-11-13): each combatant carries a kit `Monster` (later `Trap`) in `content`, plus `attribution` for encounter adjustments. The engine and combat UI read it only through `src/common/combat/facts.ts`. Campaign creatures are kit records; published ones are the content pack's kit entries as-is (below, served as `compendium.kitGet('monster')`). A clone never stands in for its published original. Encounter templates, themes, level adjustment, and minions apply to the kit monster (`src/common/rules/adjust-monster.ts`). Main builds an encounter's combatants on `COMBAT_INIT` and serves the encounter editor's row previews (`src/main/combat/encounter-combatants.ts`). Combat panels render the kit monster through `components/combat/combat-view.ts` / `components/creature/kit-view.ts`. Encounters also hold traps (`Encounter.traps`, `campaign/EncounterTraps.tsx`); traps enter combat as `kind: "trap"` combatants, hidden unless their row is visible. Traps without initiative stay out of the order, in the Triggered traps strip (`combat/TriggeredTraps.tsx`). HP-less traps are stopped with Disable, never by damage (`facts.hasHitPoints`, `facts.isDefeated`). Countermeasures (2026-11-14, `combat/TrapCountermeasures.tsx`, logic in `src/common/combat/countermeasures.ts`): the trap panel lists each printed countermeasure with its v15 clause facts (checks and DCs, action, an attackable part's defenses and HP) and its action: Disable and Destroy stop the whole trap, Delay is logged, a skill challenge counts Successes/Failures (`CombatantState.countermeasures`) and its last success applies its effect; the Triggered traps strip has the same actions, one row each. Stopping the whole trap is the DM's click, since many countermeasures stop only part of it. Published traps carry these clauses from the content pack (the UI suites use invented traps, `tools/ui-smoke/fixtures/content-repo`). Locations note traps too (`Location.traps`, references only), shown as collapsible statblocks on the location page and in the map's location sidebar (`campaign/LocationTraps.tsx`; shared trap references and search in `trap/trap-refs.tsx`). Encounters linked to a location also get its traps (hidden, counted in XP). Diseases: power cards show chips for the diseases their text names (`disease/disease-refs.tsx`, rules in `src/common/rules/diseases.ts`); in combat the disease name in a power's text applies like a condition (click it, then the PCs to expose); a disease is one kind of a PC's lasting conditions (below); the encounter editor lists its diseases.
- **PC lasting conditions** (2026-11-14, `src/common/rules/pc-conditions.ts`): `PlayerCharacter.conditions` is the PC's global set of what outlasts an encounter, a tagged union open to more kinds: `disease` (a disease reference, exposed or a stage), `condition` (a standard 4e condition with an optional "until" note), and `effect` (anything the DM names: a curse, a boon). Combat is an overlay on that set: when a PC joins combat, main copies its lasting conditions onto the combatant (`AppliedCondition.carried`, indefinite duration; diseases show their stage text), the encounter's own conditions go on top, and nothing is written back (disease exposure is saved to the PC at once). Edited in `PcConditionsDialog` (`campaign/PcConditions.tsx`: one search adds a condition or a disease, anything else names an effect), opened from the Home board's Party row. Old `diseases` lists move into `conditions` when a campaign opens (`src/main/data/legacy-pc-diseases.ts`); the Library's usage count still reads them in campaigns not opened since.
- **Effects vs Conditions**: Conditions = 4e conditions defined in `src/common/rules/dnd4e.ts`, automated by the combat engine. Effects = DM-created ad-hoc during combat that can apply/remove Conditions; a power card's clause can also apply one (a penalty, a resistance: a `custom-` condition with its label).
- **Power cards** (2026-11-13, card passes 1 and 2 (2026-11-14) of the "Monster Power Cards: Proposal" doc): `creature/PowerCardView.tsx` draws powers, traits, and auras everywhere (viewer, combat panels, reaction tiles, pinned cards, item/trap stat blocks) from a `PowerCardEntry` (`creature/power-card-entry.ts`); stat block projections attach each entry's kit trait, aura, or power as `_kit` (`kit-view.ts` `withKit`), and a card with `kit` is drawn from it (`creature/card-lines.ts`: book order, keyed lines, each later attack with its own attack row), others through the kit's `groupLines` with structured damage leading Hit. What it shows (icon names, usage chip, defense abbreviations, line order) comes from the kit's `power-card.ts` (`@kit`, moved there 2026-11-14); icons are `lucide-react` through `shared/Icon.tsx` (`Icon` resolves any Lucide name; `Glyph` draws a Lucide name or falls back to text, for condition, mark, and damage-type icons that a DM may set to an emoji). In combat the card takes `uses`/`onUse`/`onRestore`/`onPin`, `selectedLevel`, and `applies`/`onApply`: click-to-apply (`combat/card-actions.ts` `cardApplies`) highlights each applicable effect clause (`src/common/combat/clause-effects.ts`) and applies a "save ends both" group together under one engine save group; text no clause covers falls back to the regex in `combat/condition-detection.ts` (Hit, Miss, Effect). The DM's edits to a line keep only the clauses the edit left alone (`src/common/authoring/clause-rebase.ts`, used by `applyPatch` for DM patches and by `adjust-monster.ts`).
- **Popouts** (2026-11-13): a `FloatingPanel` with `popoutKey` has an "open in its own window" button. `shared/popout-window.ts` opens a blank `popout:<key>` child window (main allows only those frame names in `setWindowOpenHandler`, `src/main/windows.ts`) and the panel's body renders into it through a React portal, so it keeps the DM renderer's stores, handlers, and `window.api`. Stylesheets (as adopted copies of the parsed rules: a cloned `<link>` sometimes never loaded in Electron 43) and `data-theme` are mirrored, keys the popout doesn't handle are forwarded to the DM window's hotkeys, and bounds are remembered per `popoutPlace` in localStorage (a convenience). Closing the window closes the panel; a panel with no close (pinned cards) goes back into the app.
- **Theming**: CSS custom properties in three layers. (1) `vendor/4e-kit/styles/tokens.css`: the tokens shared with 4ecb (`--background`, `--surface`, `--text`, `--muted`, `--border`, `--accent`, `--danger`, `--power-*`, `--font-ui`/`--font-display`/`--font-card`, `--radius`), a light set plus a dark set selected by `<html data-theme="dark">` (with no attribute, the OS decides). (2) `src/renderer/styles/theme.css`: app tokens derived from the kit ones (`--hp-*`, `--cond-*`, `--player-*`, `--sb-*`, `--on-fill`, `--text-secondary`, ...); the legacy `--color-*` aliases were removed 2026-11-13. (2b) `components.css`: shared component classes after 4ecb's primitives (`btn*`, the `Modal` dialog contract, `data-table`). (3) `global.css`: element defaults, EB Garamond (`@fontsource/eb-garamond`). Both windows import `global.css`.
- **Theme preference** (system / light / dark, default system): main owns it in `<userData>/app-settings.json` (`src/main/data/app-settings-store.ts`, atomic write), sets Electron's `nativeTheme.themeSource` to it, and broadcasts `SYNC.APP_SETTINGS` to both windows on change (`CMD.SETTINGS_SET_THEME`). Each window runs `initThemeSync` (`src/renderer/theme.ts`), which resolves the preference with the kit's `resolveTheme` and sets `data-theme`. The Player window follows the DM's choice. Not in localStorage.
- No router — ContentArea switches on Zustand store state.

## Implementation Status

The application is functional across its main workflows:

- Campaign data and entities are stored as human-readable JSON with atomic writes and differential renderer broadcasts. Creatures, items, traps, diseases, templates, and themes are kit-native campaign records: a `CampaignRecord` envelope (`id`, timestamps, optional `basedOn`, kit `content`, optional `art` with image, token, and token crop) in `campaigns/<id>/{creatures,items,traps,diseases,templates,themes}/`. Legacy creature and item files convert when a campaign opens (`src/main/data/legacy-creatures.ts`, `legacy-items.ts`; originals kept as `_legacy-<file>.json`). Their compendium pages (`compendium/RecordCompendium.tsx`, kinds in `record-kinds.tsx`), including Creatures (`MONSTER_KIND`: `creature/MonsterStatblock.tsx`, the creature viewer and the benchmark editor through `monsterToEditor`/`monsterFromEditor`, with art and pop-outs), list published and Custom entries with the Creatures page's edit semantics (clone on first edit, autosave, delete), and published entries render through `compendium.kitGet` (converted to the kit). Campaign templates and themes apply in encounters via `creature/template-catalog.ts` (custom refs `campaign:<id>`).
- The Library (2026-11-14, TODO section 11, `docs/shared-library-plan.md`): labelled **Shared** in the UI (2026-11-14: the chip, the source filter, tooltips, pickers; "Library" stays the name in code, on disk, and in the agent API);custom entries of all six kinds outside every campaign, in `<userData>/library/{creatures,...}/` as the same record envelopes plus `library/assets/images/` (`src/main/data/library-store.ts`). Entity and image commands take a `home` ("library", `LIBRARY` in `campaign-records.ts`); `CMD.LIBRARY_STATE` and `SYNC.LIBRARY_UPDATE` feed the DM window's `stores/library-store.ts` with or without a campaign; `IMAGE_GET` falls back to the Library's images. Campaigns use Library entries live, like published ones: `libraryId` on encounter creature rows, encounter and location traps, and PC diseases, `library:<id>` for templates and themes, resolved by main in `encounter-combatants.ts` (`EncounterSources.library`) and by the renderer's trap, disease, and template helpers; the merged creature index lists them as source "Library". Compendium pages list published, Library, and campaign entries sorted together, with no home label on rows (2026-11-14: the labels were noise); a **source** filter after the kind's own filters narrows to Published (then a book; a magazine's issues are one choice) or Custom (then Shared or the campaign); `New` goes into the open campaign (the Library with none open). The entry's controls sit in its stat block title bar after the name (`shared/record-header.tsx`, a slot every kind's viewer and editor header renders): its home chip, then same-size icons: pop out, Edit (pressed while editing; press again, or `e`, for done), and a ⋯ menu with **Shared with every campaign**, Duplicate, and Delete. The shown entry is a pane (`compendium/EntryPane.tsx`: `useEntryPane`, `EntryView`); pop out moves it, preview or editor, into an OS window of its own (`PoppedEntry`, through `usePopoutWindow`) with the same controls and its own `e`, and every kind can pop out. Sharing moves the entry between the open campaign and the Library under the same id, with its art, this campaign's references (`rehomeRefs`, `REFERENCED_FROM` in `campaign-records.ts`), and its working copy (`DraftStore.rehome`); main's `move-entry.ts`, `CMD.ENTRY_SHARE`. Taking it back is refused while another campaign uses it. Duplicate copies beside the entry (`basedOn: library/<type>/<id>` for a Library source; a campaign is never a source). Deleting a Library entry names the campaigns that use it (`CMD.LIBRARY_USAGE`). Every working copy has exactly one home, fixed at creation (`/destinations` is not patchable); deleting a campaign archives its working copies and startup archives orphans. A future campaign export must bundle the Library entries it references (handling of entries the importer already has is TBD in the plan).
- Campaign management includes creatures, encounters, locations, items, maps, player characters, images, and compendium browsing/editing. Campaign items, traps, diseases, templates, and themes are kit records (`CampaignRecord` envelopes, `src/common/campaign-records.ts`) edited on their compendium pages (`RecordCompendium`). Legacy campaign items convert when a campaign opens (`src/main/data/legacy-items.ts`; originals kept as `_legacy-<file>.json`).
- Character import (2026-11-13, TODO section 7): Character Builder `.dnd4e` saves (and `.4ecb` backups once 4ecb writes `snapshots` into them) import as a kit `CharacterSnapshot` on `PlayerCharacter.sheet` (`src/common/character/character-import.ts`, with a small in-house XML reader in `src/common/utils/xml.ts`; `CMD.PC_IMPORT` in main applies them, matching re-imports by `sourceId` or the PC the DM picked). Stats only, no powers; players keep tracking their own HP. The combat panel (`campaign/PcSheet.tsx`), the PC's initiative row, and the attack-resolve row show the sheet's numbers. The PCs page (2026-11-14, `campaign/PCListView.tsx`) is the campaign's character library, laid out like a compendium page (`.compendium-split`): a list searched by character and player name and sorted by character, player, race, class, or level (rows: active toggle, token, character, player, race, class, level), beside the selected PC's pane (name, chip color, import and delete icons after the name, level at the right, active and player name, portrait and token editor, the imported sheet's rows and class mark). It shows no party level, level warnings, or diseases: those concern the active party, on the Home board. A PC with a sheet shows its class and level from the sheet, and its class mark comes from the sheet's class features (`pcMarkType` in `src/common/rules/class-marks.ts`); a PC without one reads "No sheet (mark)" in its row with the mark dropdown, and sets its level in the pane.
- The combat tracker includes initiative entry and reordering, current/inspected stat blocks, damage/healing, conditions and effects, click-to-apply from power cards driven by effect clauses (2026-11-14; "save ends both" groups applied together, a regex fallback for text without clauses), delay/ready actions, reaction tracking, turn automation, and combat logging.
- A campaign's Home is the session board (2026-11-14, `campaign/HomeView.tsx`): a one-page reference that never scrolls and has no editable fields; its rows link to the pages that edit, and its controls may open dialogs that edit (a PC's lasting conditions: `PcConditionsDialog` in `campaign/PcConditions.tsx`, opened from a condition chip or the + in the Party row). Its panels are stat block panels with striped lists like the compendium's (`.sb-columns`, `.sb-list-row` in `statblock.css`). It shows the combat in progress with Resume, the active party under "Party (Level N)" with the active player count at the header's right (portrait, defenses and passive Perception/Insight from imported sheets, and Conditions: its lasting conditions as chips, plus, in combat, the encounter's own conditions on that PC as condition pills), and recently changed entries, a stat block panel per kind side by side (PCs excluded) newest first, as many rows as fit the remaining height. The sidebar's Campaign section links Locations directly (the old Home count cards were its only route).
- Party level is derived, not stored (2026-11-14, `src/common/rules/party.ts`): each PC's level is its imported sheet's, or `PlayerCharacter.level` set in its PCs page pane when it has no sheet; the party level (encounter editor budget, difficulty bar, level warnings; Home board) is the most common level among the active PCs, the higher on a tie. On the Home board's Party panel, a warning icon in 4ecb's style (`campaign/level-warnings.tsx`, with short tooltips; the books' fix for a PC off the party level is DMG2 p.34, "Making Things Level") flags active PCs off the party level or without one. Opening a campaign that still has the old `partyLevel` in campaign.json gives it to the PCs without a sheet or level and drops it (`src/main/data/legacy-party-level.ts`).
- Rewards by level frame (2026-11-16, `src/common/rules/treasure.ts`, `rewards.ts`, `src/renderer/components/rewards/`, `treasure/`): a campaign spans several levels, so encounters and treasure are planned per **level frame**, the party level they are for. An encounter's is `Encounter.level`, set to the party's level when it is made and edited in the encounter editor's subheader; the editor's budget, difficulty bar and row warnings use it (the party's level now shows beside it when they differ), and an encounter without one counts at the party's level now (`encounterFrame`). A treasure's is `Treasure.level`. Each treasure is a record in `campaigns/<id>/treasure/` (an item reference, `ItemRef` with `itemLevel` for a multi-level item, or money as text and gp; optional slot; a location or encounter; found). Location and encounter pages list and add the treasure placed there (`TreasureSection`; an encounter's new treasure takes its level). The sidebar's **Rewards** page (`RewardsView`, like the Home board a view of records kept elsewhere) lists levels (XP per PC, items, gold, treasure mode) beside the selected level's pane: its encounters (XP from main's `encounterXp`, `CMD.COMBAT_ENCOUNTER_XP`, rows resolved as combat would; "+ New encounter" plans one for the level), a meter (`RewardsMeter`: XP per PC against what the next level takes, PHB p. 29 / RC p. 85; magic items and gp, money and consumables at their price per DMG p. 126, found / placed / not placed against the treasure budget), and its treasure. Per level the DM picks how treasure is budgeted (`LevelPlan` in `levels/<level>.json`, the place for per-level settings): DMG parcels (slots derived from DMG pp. 125-129 and the active party's size), RC rolls (RC pp. 298-302: ten treasures rolled into slots and stored), or free (the bars use the DMG budget). Suggest fills empty slots (items at random from those with a version at the slot's level, of the rolled rarity when one exists). Library items count as used by treasure (`REFERENCED_FROM.item`). Only the tables' numbers are in the source; the parcels' wording stays in the books. Item index rows carry each version's level and price (`ItemIndexEntry.versions`, index version 2). Nothing about rewards reaches the Player window.
