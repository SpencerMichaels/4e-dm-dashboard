---
name: 4e-author-content
description: Iteratively create or revise D&D 4e creatures, items, traps, diseases, monster templates, and monster themes with the 4e DM Dashboard. Translate creative intent into explicit rules and numbers, submit drafts, and incorporate DM edits and comments.
---

Use the dashboard's authoring tools (MCP or the repository CLI). Read `docs/AUTHORING.md` in the dashboard repository for setup and command examples. The external agent does the creative work; the dashboard calculates, validates, keeps the version history, and writes each valid version into the campaign.
To work on what the DM has open, call `current_entry`: a campaign entry comes with `draftId`, its working copy (read with `get_draft`, edit with `patch_draft`, comment with `comment`); a published one with `publishedId` (fetch it to read it; to change it, `create_draft` with `from` set to its search key makes a campaign copy that records its source and art, exactly as the DM's Copy to campaign does). `edit_entry` gives the working copy of any campaign entry by id. The DM sees your edits and comments live in the stat block.


1. Capture the concept, level/role/rank, strengths, weaknesses, non-negotiable mechanics, and encounter context. Identify where it belongs (`destinations`): a campaign, or the Library, custom entries shared by every campaign and used live wherever they appear (kind `monster` is a creature). New content goes into the campaign open in the dashboard; use the Library (`destination: "library"`) only when the DM asks for content shared across campaigns. Do not assume the open campaign is where an existing entry lives: `current_entry` says (campaignId "library" for a Library entry). For updates, fetch `destination_entity` and record its hash.
2. Find precedents using the sibling `4e-find-precedents` skill or its search workflow. Always consult the local game data corpus (`search`/`fetch`, or `search-local` offline) before any web search; use the web only as a last resort, as that skill describes. Fetch complete source context before relying on a match. A source is evidence for a mechanic, not proof that the new combination is balanced.
3. Use `scaffold` and `benchmarks`; the numeric policy is `published-rules-v2` (the latest published rule for each number: DMG roles, the MM3-era DMG errata for damage and accuracy, DMG2 elites, solos and minion damage, Rules Compendium DCs; see `benchmarks` output). Interpret qualitative preferences as explicit proposals (accuracy offsets, low/high damage bands, HP adjustments), with rationale. Do not invent an official exchange rate between damage, accuracy, control, and defenses. For items, call `benchmarks` with `kind: "item"` for the table price, enhancement bonus, and version ladder; consumable prices and all item effects require item-specific precedents. Monster bands do not apply to items.
4. Preserve prose in kit `Line.text` and derive clauses from it. Supply `quote` instead of counting `at` spans. Preserve exact conditions, targets, triggers, and durations. Unsupported text can be `{text: "exact text"}` in clauses. Read the kit schema and `src/common/authoring/spans.ts` when needed; never invent schema fields or claim structured mechanics automatically execute in combat (in combat the DM clicks a clause's highlighted words to apply it). The DM's own edits to a line drop the clauses whose words they touched, so when you work on an entry, fill clauses for printed text no clause covers.
5. `create_draft` records content and intent (or copies an entry with `from`: a published search key, `library/<kind>/<id>`, or `campaign/<campaignId>/<kind>/<id>`), and every version you write goes straight into the entry (in the campaign open in the dashboard, or the Library when you pass `destination: "library"` or no campaign is open), so the DM sees it in their compendium at once. An edit to a Library entry changes it in every campaign that uses it; when the DM wants a change for one campaign only, copy it into that campaign instead. Record confirmed choices in `decisions` and explicit numeric choices in `recipe`. `suggest_numbers` returns a revision-bound proposal that leaves DM-edited fields unchanged. Apply coherent text/metadata changes with `patch_draft`; damage suggestions require rewriting hit prose and clauses together.
6. Ask focused questions where timing, ownership, scope, or termination materially changes the design. Offer alternatives with consequences. Record open questions with `comment(question=true)`. Give every comment the most specific `target`: the power, trait, or aura node (`/content/powers/@ID`) or stat field (`/content/hp`, `/content/defenses`) it concerns. The DM sees it next to that line of the stat block; a comment with no such target is refused. Ask about the creature as a whole (destination, encounter context) in chat, not with `comment`. Ask one question per comment. Continue independent work while waiting. Record answers from chat in `decisions`. When one of your questions is answered (in chat or the dashboard) or a redesign makes it moot, close it the same turn: `comment(replyTo, resolve=true)` with a reply stating the answer and its revision, or why it no longer applies. A question with several parts stays open only for the unanswered part; prefer separate questions so each closes on its own.
7. Run the sibling `4e-review-balance` skill. Submit its findings for the exact content revision, then `open_review`. The DM can edit fields directly or leave comments. There is no approval step: do not call a version final until the DM says so.
8. On continuation, always `get_draft` again. DM edits (`overrides`) and confirmed choices are the DM's direction: build on them rather than reverting them, revise one when the DM asks or a requested change requires it, and say what changed in a reply. Use stable node IDs from `nodes`: `/content/powers/@ID/attacks/0/hit/text`. Use `/append/powers`, `/remove/powers/@ID`, and `/order/powers` for structural edits. A revision conflict lists the fields the DM changed since your version: fetch the draft again, and if your change touches any of them, ask the DM which version to keep before patching; never retry an old snapshot over DM edits.
9. Reconcile edited prose and metadata. Mark a node in `reconciled` only after checking its current interpretation; explicit unparsed/manual handling is acceptable. Keep every comment and reply to one or two sentences; the DM reads them in small popovers beside the stat block. Put rationale in `decisions` and analysis in the review, not in threads. The `description` is plain text, like every published entry's: paragraphs separated by blank lines, no Markdown headings, bullets or bold (`validate` flags them). Keep it to what the DM reads at the table: tactics and counterplay; design notes go in `decisions`. When you act on DM feedback, reply leading with "Done in revision N:" and what changed (or "No change:" and why) so the DM can resolve it in one click; only the DM resolves DM threads. On continuation, check every open thread you started and close any that are answered or moot. A fresh content revision requires a fresh balance review.

Check `sync_status` before saying a version is in the campaign: a version that could not be written (for example, the entry was deleted) has an `error` saying why. Changes the DM makes to the entry outside the session fold into the draft; `get_draft` shows them. To undo a change the DM dislikes, `restore_draft` an earlier version (from `versions`), or patch it back. If disconnected, provide the draft ID and resume later. If an unsupported feature requires engine/schema changes, describe that gap and retain its rule text; content authoring alone does not authorize modifying application code.
